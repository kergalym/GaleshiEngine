Third-person demo: camera, capsule, and animation

Set up the sample hot-reload C++ controller: a non-physical Player visual root, a dynamic physics proxy, camera-relative movement, and gameplay signals.

In this tutorial

  • Scene setup

1. What the demo does

  • Finds or creates a non-physical Player visual root.
  • Finds or creates a separate PlayerPhysics entity with a dynamic capsule body.
  • Switches the gameplay camera to third-person orbit.
  • Moves the physics proxy relative to the camera, then copies its position to the visual Player root.
  • Supports sprinting, jumping, respawning, and a simple attack trigger.
  • Rotates the visual Player toward the movement direction.
  • Sends optional animation parameters for speed, jump, attack, and respawn.
  • Plays optional footstep and attack sounds and creates a small HUD canvas.

The complete source is third_person_demo.cpp.

2. Scene setup

  1. Ground. Use a landscape or a large ground mesh with a static collider. The physics proxy needs collision to stand and jump.
  2. Camera. Choose Create → Camera. Keep the name Camera (or edit kCameraName in the script) and mark it Primary. If it is not parented, the script attaches it to Player.
  3. Player. Create an entity named Player with a visible mesh/model, and do not add a rigid body or collider. This root is the visual and camera target; it must remain non-physical.
  4. Physics proxy. The script creates PlayerPhysics at the Player's feet plus the capsule center offset. If you author it manually, make it a root entity with a dynamic capsule collider and rigid body.
  5. Script. Copy third_person_demo.cpp into <project>/scripts/ or <project>/assets/scripts/.
  6. Open the project, wait for the C++ script to compile, and press Play.

Player vs PlayerPhysics. The visual root must not have a rigid body, or Jolt will overwrite its position and rotation. Movement happens on the physics proxy; the script copies the proxy position back to the visual root.

3. Add the script

The demo is a hot-reload C++ module. It exports the same lifecycle as any other module: 

extern "C" void GaleshiScriptRegister(const GaleshiScriptApi* api);
extern "C" void GaleshiScriptUpdate(float dt);

If the project already has another module using those exports, add this file as a separate module rather than copying its functions into an existing file. The hot-reload worker can load more than one module, but each shared library must export a complete module.

Compile diagnostics appear in the Code Editor Output and Errors tabs. The demo does not link the engine; it uses only the public script API.

4. Controls

InputAction
WASDMove relative to the third-person camera.
Left ShiftSprint.
SpaceJump.
Left mouseAttack trigger.
RRespawn at the spawn point.

Input is read only while Play mode is active. The Player root stays at the scene root; the script writes its position in world coordinates.

5. Tuning

The top of the script contains the main constants. Start there before changing the controller logic: 

constexpr const char* kPlayerName = "Player";
constexpr const char* kPlayerPhysicsName = "PlayerPhysics";
constexpr const char* kCameraName = "Camera";
constexpr const char* kPlayerModel = "assets/models/player.glb";

constexpr bool kAutoCreatePlayer = true;
constexpr bool kAutoCreatePhysicsProxy = true;
constexpr bool kAutoParentCamera = true;

constexpr Vec3 kSpawn{0.0f, 2.0f, 0.0f}; // Player feet
constexpr float kWalkSpeed = 4.5f;
constexpr float kRunSpeed = 8.5f;
constexpr float kJumpSpeed = 7.0f;
constexpr float kCapsuleHalfHeight = 0.85f;
constexpr float kCapsuleRadius = 0.35f;
constexpr float kCapsuleCenterY =
    kCapsuleHalfHeight + kCapsuleRadius;

kSpawn is the visual Player position (feet). The physics proxy is placed at kSpawn.y + kCapsuleCenterY because a Jolt capsule is centered on its body origin.

Model facing direction

The controller rotates the player toward the movement direction. If your model faces -Z, set: 

constexpr float kModelYawOffset = 3.14159265f;

If the character runs sideways, adjust the offset further. The model path is only used when the script creates the visible player automatically.

6. Animation, audio, and HUD

The script sends these optional animation signals to the player's state machine:

SignalUse
Speed (float)Normalized horizontal speed.
JumpTrigger/parameter for a jump transition.
AttackTrigger/parameter for an attack transition.
RespawnTrigger/parameter for a respawn transition.

The calls are ignored safely if the player has no animation component. Set up matching parameters and transitions in the ASME window; see Animation state machines.

Optional audio

assets/sounds/footstep.wav
assets/sounds/attack.wav

Missing files produce no audible result. Set the path constants to empty strings to disable the calls.

HUD

The script creates a canvas named ThirdPersonHUD with a text widget named status. It shows horizontal speed, grounded or airborne state, and whether PlayerPhysics has a rigid body. Reloading the script reuses the existing canvas and widget instead of creating duplicates.

7. Limitations

  • Ground detection uses vertical velocity, not a raycast.
  • Jumping is a simple vertical velocity impulse.
  • Attack has no hit detection, damage, combos, or networking.
  • Camera auto-parenting only finds a root camera named Camera.
  • The Player root must stay unparented; its position is copied from the proxy in world space.
  • Only one player and one PlayerPhysics are controlled.
  • Camera collision, root motion, and network prediction are outside the sample.

These limitations are deliberate: the example stays small enough to read while exercising world, input, physics, camera, animation, UI, and audio APIs.
