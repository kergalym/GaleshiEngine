Native vs hot-reload C++: choosing the right path

Both paths are C++, but one links the engine and the other runs in an isolated worker. Pick the path that matches what the code needs to touch.

2. Native API

The native API is the public C++ class surface of the engine. Include the umbrella header and link the engine target: 

#include <GaleshiEngine/GaleshiEngine.hpp>

target_link_libraries(MyGame PRIVATE GaleshiEngine::GaleshiEngine)

It exposes real engine objects: Scene, Entity, ECS components, AssetManager, RenderSystem, EnginePhysicsSystem, AudioSystem, ScriptEngine, and more. Editor-only classes such as ContentBrowser and EditorState are intentionally excluded. 

#include <GaleshiEngine/GaleshiEngine.hpp>

class MyGame final : public Galeshi::Application {
protected:
    void OnStart() override {
        m_physics.Init();
        m_context.scene = &m_scene;
        m_context.assets = m_assets.get();
        m_context.renderer = GetRenderer();
        m_context.input = &GetInput();
        m_context.physics = &m_physics;
        m_context.audio = &m_audio;
    }

    void OnUpdate(float dt) override {
        m_physics.Update(m_scene, dt);
        m_audio.Update(m_scene, dt);
    }

private:
    Galeshi::Scene m_scene;
    std::unique_ptr<Galeshi::AssetManager> m_assets =
        std::make_unique<Galeshi::AssetManager>();
    Galeshi::EnginePhysicsSystem m_physics;
    Galeshi::AudioSystem m_audio;
    Galeshi::Api::EngineContext m_context;
};

EngineContext is an optional non-owning grouping of subsystem pointers. It does not create, own, or update anything; the game keeps explicit ownership and lifetime.

Use native C++ when you need:

  • real engine objects and pointers;
  • custom rendering or asset pipelines;
  • direct entt access;
  • control over subsystem lifetime;
  • maximum in-process performance.

3. Hot-reload scripts

Hot-reload scripts live in scripts/ or assets/scripts/. The editor compiles them into temporary shared libraries and runs them in a separate worker process. The worker does not link the engine and does not own the scene or GPU resources. 

#include "GaleshiEngine/Scripting/CppGameplayApi.hpp"

static Galeshi::Script::Api* g_api = nullptr;

extern "C" void GaleshiScriptRegister(const GaleshiScriptApi* api) {
    static Galeshi::Script::Api wrapper(api);
    g_api = &wrapper;
}

extern "C" void GaleshiScriptUpdate(float dt) {
    if (!g_api || !g_api->Compatible()) return;
    (void)dt;

    const uint32_t player = g_api->world.Find("Player");
    if (!g_api->world.Valid(player)) return;
    g_api->physics.SetVelocity(player, {0.0f, 0.0f, -5.0f});
}

The host passes a table of function pointers. Script calls are forwarded to the editor process as worker requests. This gives crash isolation, module unloading, hot reload, and a stable boundary that does not require linking the engine.

Use hot-reload scripts when:

  • the code is gameplay or level logic;
  • fast iteration and hot reload matter;
  • crash isolation is useful;
  • the script API covers what you need;
  • handles instead of raw pointers are acceptable.

4. Why extern "C"?

The worker loads a module with dlopen and finds symbols with dlsym. A normal C++ function has a compiler-dependent mangled name: 

void GaleshiScriptUpdate(float dt);
// emitted as something like _Z19GaleshiScriptUpdatef

extern "C" gives the exported function a stable C symbol name: 

extern "C" void GaleshiScriptUpdate(float dt);
// emitted as GaleshiScriptUpdate

It does not mean the file is C. Templates, classes, and STL are fine inside the module. Only the boundary is C-like; C++ objects do not cross the shared-library boundary.

5. Choosing a path

If the code...Use
Is part of the game executable or a native pluginNative API
Needs direct scene, renderer, or ECS accessNative API
Owns physics, audio, or rendering systemsNative API
Is gameplay logic that should reload quicklyHot-reload scripts
Should survive script crashes independentlyHot-reload scripts

A project can use both: native systems in the game application and hot-reload scripts for gameplay behavior.

6. Common mistakes

  • Including GaleshiEngine.hpp in a hot-reload module. Including the header does not link the engine into the worker. Use CppScriptApi.hpp or CppGameplayApi.hpp instead.
  • Assuming extern "C" means C. The translation unit is still C++.
  • Storing raw engine pointers across the worker boundary. Use entity ids and API operations.
  • Calling the API before registration. Assign g_api in GaleshiScriptRegister.
  • Ignoring ABI checks. New scripts should check Compatible() or the ABI version before using recently added calls.
