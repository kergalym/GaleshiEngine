Tutorial 7

Hot-reload C++ gameplay scripts

Write gameplay logic in C++, compile it into a worker process, and reload it without restarting the editor.

In this tutorial

  • Where scripts live

1. Where scripts live

Place .cpp, .cc, or .cxx files in the project's scripts/ or assets/scripts/ directory. The editor compiles changed files into temporary shared libraries and loads them into a separate GaleshiScriptWorker process.

The worker contains the script code but not the editor scene, renderer, or GPU resources. A crash, hang, or compile error in a script does not take down the editor process.

2. Required exports

A script module must export two C-linkage functions. The signatures are fixed because the worker loads them by symbol name: 

#include "GaleshiEngine/Scripting/CppScriptApi.hpp"

static const GaleshiScriptApi* g_api = nullptr;

extern "C" void GaleshiScriptRegister(const GaleshiScriptApi* api) {
    g_api = api;
    g_api->log(g_api->user, "script registered");
}

extern "C" void GaleshiScriptUpdate(float dt) {
    (void)dt;
    // gameplay code
}
ExportWhen it runs
GaleshiScriptRegisterOnce when the module is loaded. Store the API table here.
GaleshiScriptUpdateEvery frame with the frame delta.

extern "C" only fixes the exported symbol name. The file is still C++, and you can use classes, templates, and STL types inside it. Engine classes cannot be linked in the worker process.

3. Using the C API table

The API table exposes entity handles and explicit operations. Entity ids are plain numbers; revalidate them before use: 

extern "C" void GaleshiScriptUpdate(float dt) {
    const uint32_t player =
        g_api->find_entity(g_api->user, "Player");
    if (!g_api->entity_valid(g_api->user, player)) return;

    const GaleshiScriptVec3 current =
        g_api->get_position(g_api->user, player);
    const GaleshiScriptVec3 target{0.0f, 2.0f, 0.0f};

    // Frame-rate independent interpolation helper.
    const GaleshiScriptVec3 next =
        VInterp(current, target, dt, 8.0f);
    g_api->set_position(g_api->user, player, next);
}

The table includes logging, input, entity lookup/validation, position and velocity access, camera mode switching, audio, particles, navigation, animation, and more. New fields are appended to the end of the ABI table for compatibility.

Scripts can create a water body by creating an entity and adding the "water" component: 

const uint32_t water = g_api->world.Create("Water");
g_api->world.SetPosition(water, {0.0f, 0.0f, 0.0f});
g_api->world.AddComponent(water, "water");

4. Using the class wrappers

CppGameplayApi.hpp is a header-only convenience layer over the same function table: 

#include "GaleshiEngine/Scripting/CppGameplayApi.hpp"

static Galeshi::Script::Api* g_api = nullptr;

extern "C" void GaleshiScriptRegister(const GaleshiScriptApi* api) {
    static Galeshi::Script::Api wrapper(api);
    g_api = &wrapper;
}

extern "C" void GaleshiScriptUpdate(float dt) {
    if (!g_api || !g_api->Compatible()) return;
    (void)dt;

    const uint32_t player = g_api->world.Find("Player");
    if (!g_api->world.Valid(player)) return;

    g_api->physics.SetVelocity(player, {0.0f, 0.0f, -5.0f});
}

New modules should check Compatible() or the ABI version before using recently added calls. The wrappers also null-check individual function pointers so older hosts fail safely.

5. Sharing values between scripts

Modules are separate shared libraries, so a normal C++ global is not shared. Use per-entity runtime variables instead: 

const uint32_t player = g_api->world.Find("Player");

// Writer module, for example a water trigger:
g_api->world.SetVariable(player, "isSwim", 1.0f);

// Reader module, for example the player controller:
const bool isSwim =
    g_api->world.GetVariable(player, "isSwim", 0.0f) > 0.5f;

Variables are floats keyed by entity and name. They are runtime-only and shared by every C++ hot-reload module in the scene. GetVariable returns the fallback when the entity or variable does not exist.

6. Trigger callbacks

A module can also export either optional callback. They are looked up when the module loads: 

extern "C" void OnTriggerBeginOverlap(uint32_t trigger,
                                      uint32_t other) {
    // trigger is the sensor collider; other is the overlapping entity.
}

extern "C" void OnTriggerEndOverlap(uint32_t trigger,
                                    uint32_t other) {
    // Fires after the last contact between the pair is removed.
}

Every loaded module with the matching export receives the event. The hook is module-level, not per-entity, so inspect the ids if one module handles several volumes. Water bodies with the Water inspector's Trigger checkbox also dispatch these events with the water entity as trigger. 

extern "C" void OnTriggerBeginOverlap(uint32_t trigger,
                                      uint32_t other) {
    if (!g_api->has_component(g_api->user, trigger, "water")) return;
    g_api->log(g_api->user, "body entered water");
    (void)other;
}

See Water triggers for the complete Lua and C++ water example.

7. Compile and reload

  1. Save the .cpp file in the project's scripts/ or assets/scripts/ directory.
  2. Open it in the Code Editor. Compile diagnostics appear in the Output and Errors tabs.
  3. Use Compile C++ to compile and reload, or wait for the editor's debounced scan.
  4. Press Play and watch the Output Log. Invalid modules are not loaded; the last successfully loaded module keeps running.

Compilation uses g++ by default. Set the CXX environment variable to override the compiler. Live syntax checks also cover .cpp, .h, and .lua files while you edit.

8. Rules and limitations

  • Do not include GaleshiEngine.hpp in a hot-reload module. The worker does not link the engine. Use CppScriptApi.hpp or CppGameplayApi.hpp.
  • Do not store raw engine pointers across the worker boundary. Use entity ids and API calls.
  • Assign g_api in GaleshiScriptRegister, not during static initialization.
  • extern "C" does not mean the file is C. It only changes the exported symbol linkage.
  • The API can only access what the host exposes. Use the native API when you need direct engine classes or custom engine work.
